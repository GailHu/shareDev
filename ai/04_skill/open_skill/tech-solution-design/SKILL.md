# 技术方案（详细设计）

技术方案不是技术路线的加长版，也不是代码的自然语言复述。它只回答一件事：**一个没参与过讨论的人，照着它能不能写出正确的代码和测试用例，而不用回来问人。** 凡是需要口头补充才能施工的部分，都是本文档的缺陷。

选型论证、备选排除、阶段门禁属于技术路线，不在此处重复。本文档默认路线已定，只管落地。

## 工作流程

### 第 1 步：定位输入并确定起点

输入按优先级取，能拿到几样取几样：**技术路线文档 > 需求文档（PRD）> 目标代码仓库**。

`.docx` 用脚本提取（Read 工具不支持该格式），脚本位于本技能目录下，调用时拼成绝对路径：

```bash
python scripts/extract_doc.py <文档路径> <输出目录>
```

输出 `content.txt`（正文与表格）和 `media/`（内嵌图片）。用 Read 工具读 content.txt，并**逐张读 media 下的图片**——状态机流程图和界面原型常含正文里没有的字段与交互分支，这些正是契约章节的直接输入。`.pdf`、`.md`、`.txt` 直接用 Read 工具。

**有技术路线时**：抽出决策编号 D1…Dn 与硬约束 C1…Cn。本方案的每个设计点都要能追溯到某条 D 或 C。技术方案无权推翻路线决策——**发现某条决策在实现层面走不通时，停止撰写，单列「路线冲突项」（冲突点 + 走不通的具体原因 + 建议的替代做法）交用户裁决**，不要在方案里自行改掉。

**没有技术路线时**：不要直接展开设计。先做一次关键决策快筛，逐项给出结论并写入第 1 章：

- 数据真值来源与一致性机制（谁是事实，谁是投影）
- 同步与异步的边界、超时与重试策略
- 鉴权与访问限制的强制点（服务端还是客户端）
- 抽象与复用边界（按哪个维度复用）
- 技术栈继承还是新增（默认继承）

跳过这步的方案会在错误的前提上把全部细节展开一遍，返工成本远高于快筛成本。若这五项中有两项以上无法定论，说明该先做技术路线，提示用户后再继续。

### 第 2 步：建立事实基线

**代码仓库是事实来源，优先级高于文档描述。** 需求文档写的字段名和实际表结构对不上时，以代码为准，并把差异记进待确认前提。

检索并记录：现有数据模型、接口风格与命名约定、错误码体系、鉴权中间件、日志与埋点规范、已有的公共组件。

后续每个设计元素都标注 **[沿用] / [改造] / [新增]**。标 [新增] 的必须写一句为什么不能沿用——这一栏能挡掉大部分无意识的重复造轮子。

### 第 3 步：冻结契约

这是技术方案的主体。**判据：契约章节写完后，前端、测试、下游服务应当可以脱离后端并行开工。做不到就是没写完。**

- **数据模型**：字段名、类型、是否可空、默认值、唯一约束、索引、时区与小数精度、软删策略。
- **接口**：路径、方法、鉴权要求、请求体与响应体的**全部字段**、分页方式、幂等键、错误码表。禁止出现「其他字段略」「等」「与现有接口一致」。
- **枚举与状态机**：枚举值就地列全；状态机给完整迁移表，并写明**非法迁移发生时的处置行为**（报错码是什么、是否记录、是否告警）。
- **共享类型**：前后端或服务间共用的结构，直接给出代码定义，不用文字描述。

### 第 4 步：链路时序与一致性

每条关键链路画时序图，并逐条标注：

- 事务边界落在哪几步之间
- 哪一步不可重入，为什么
- 失败在第 N 步时，前 N-1 步已产生的副作用如何回收
- 超时时间与重试次数，以及**配套的幂等键**

**「失败后重试」单独出现即不合格**，必须同时给出幂等机制，否则重试就是制造重复数据。

### 第 5 步：穷举异常与边界

按 [checklist.md](checklist.md) 的扫描表逐类过一遍，每条写三件事：**触发条件 / 系统行为 / 用户可见表现**。

设计文档最常见的失败不是写错，是没写到。缺失的分支在编码期会被每个人按各自理解补齐，产出彼此不一致的行为，而且不会有人报错。这一步的篇幅通常应当超过正常流程的描述。

### 第 6 步：非功能落地

- **性能预算**：把路线或需求里的端到端指标拆到每一跳（数据库查询、外部调用、序列化、网络），各跳预算之和须给端到端上限留出 30% 余量。只写总指标不拆解等于没写。
- **可观测性**：**第 5 步列出的每个失败模式，至少配一个可观测信号**（日志字段、指标、告警阈值）。逐条反查，查不到信号的失败模式就是线上黑洞。
- **安全**：鉴权强制点、越权访问的具体用例、敏感字段的脱敏规则与落盘范围。
- **兼容与迁移**：数据迁移脚本、新旧版本并存期的行为、回滚路径。**回滚方案不能是「重新发一次旧版本」**，要写清已写入的新格式数据如何处理。

### 第 7 步：任务拆分与验收

每个任务写四项：产出物、依赖的前置任务、**可执行的验收标准**、预估工时。按契约先行的顺序排列，契约类任务完成前不安排依赖它的并行任务。

验收标准要能被第三方判定。「功能完成」不是验收标准，「调用 X 接口传入越界分页参数返回 400 且错误码为 Y」才是。

### 第 8 步：待确认前提

信息缺失不阻塞产出。写成「待确认项 + 影响范围 + 默认假设」，标注确认后升版。**不要因为缺信息反复追问用户，也不要静默假设。**

## 输出

按 [template.md](template.md) 的结构撰写，文件名 `<项目名>-技术方案-v0.1.md`，默认写入当前工作区根目录。

给用户的回复里要点出三样东西：本方案落实了技术路线的哪些决策（无路线时说明快筛结论）、契约中风险最高的一处及原因、还有哪些前提待确认。

## 交付前自检

三问全过才算技术方案：

1. **能否照着直接写代码？** 随机抽一个接口，检查请求与响应字段是否完整到可以直接定义类型。文中出现「等」「视情况」「参考现有实现」「按需处理」即不合格。
2. **能否照着直接写测试用例？** 随机抽一条业务规则，检查是否给出了边界值、非法输入、并发情形下的预期行为。
3. **线上出问题能否定位？** 从第 5 步的异常清单里随机抽一条，检查第 6 步是否有对应的可观测信号。

补充检查项：

- [ ] 每个设计点可追溯到某条路线决策 D 或硬约束 C
- [ ] 每个设计元素标了 [沿用] / [改造] / [新增]，[新增] 都写了理由
- [ ] 接口响应字段无省略，错误码表完整
- [ ] 状态机含非法迁移的处置行为
- [ ] 每处重试都配了幂等键
- [ ] checklist.md 的每一类都过了一遍
- [ ] 每个失败模式都有可观测信号
- [ ] 每个任务的验收标准可被第三方判定
- [ ] 未知信息进了待确认前提，而不是被静默假设
- [ ] 没有混入选型论证与备选方案比较（那属于技术路线）
