# tech-solution-design

一个Agent Skill：把技术路线或需求文档转成一份**可直接施工**的技术方案（详细设计）。

## 它解决什么问题

大多数"技术方案"读起来完整，一动手全是问号：接口响应字段写了一半、状态机没写非法迁移怎么办、"失败后重试"没配幂等键、异常分支缺失后被每个开发按各自理解补齐。

这个技能把交付标准定死为一句话：**一个没参与过讨论的人，照着它能不能写出正确的代码和测试用例，而不用回来问人。**

配套三条交付前自检：能否照着直接写代码？能否照着直接写测试用例？线上出问题能否定位？三条都答不上来，产出的就只是说明文档。

## 与 tech-roadmap-from-prd 的分工

| | 技术路线 | 技术方案 |
|------|----------|----------|
| 回答 | 走哪条路、为什么、什么信号说明走错了 | 这条路具体怎么修、照着能不能写代码 |
| 产出单位 | 关键决策（选择/依据/排除/前提/重评触发/验证节点） | 契约、时序、异常行为、任务与验收 |
| 判定标准 | 能否用它否决一个提案 | 能否照着它写出代码和测试用例 |
| 选型论证 | 有 | **没有**，写进来即不合格 |

典型链条：PRD → 技术路线（锁死不可逆的选择）→ 技术方案（落到可编码粒度）→ 排期。

## 安装

本技能已位于 `<仓库根>/.cursor/skills/tech-solution-design/`，随仓库共享。

要改为个人技能（所有项目可用），把整个目录移到 `C:\Users\<用户名>\.cursor\skills\`。

> 不要放进 `~/.cursor/skills-cursor/`，该目录由 Cursor 内置技能占用。

安装后重启或新开一个对话即可生效。

## 使用

**自动触发**：给出输入文档并提出要求即可，例如

```
g:\docs\xxx-技术路线-v1.0.md 按这份路线出一份技术方案
g:\docs\xxx产品-PRD.docx 帮我写详细设计文档
```

**显式调用**：在对话中点名 `tech-solution-design`。

若不希望自动触发，在 `SKILL.md` 的 frontmatter 中增加一行：

```yaml
disable-model-invocation: true
```

## 工作流程概览

1. **定位输入** — 技术路线 > PRD > 代码仓库。有路线则抽 D/C 编号做追溯；无路线则先做五项决策快筛
2. **建立事实基线** — 代码优先于文档，每个元素标 [沿用]/[改造]/[新增]
3. **冻结契约** — 判据是前端与测试能否脱离后端并行开工
4. **链路时序与一致性** — 事务边界、不可重入步骤、失败回收、重试必配幂等
5. **穷举异常与边界** — 按 checklist.md 逐类扫描，篇幅通常超过正常流程
6. **非功能落地** — 性能预算拆到每一跳、每个失败模式配可观测信号、回滚含数据处理
7. **任务拆分与验收** — 验收标准须能被第三方判定
8. **待确认前提** — 信息缺失不阻塞产出

## 提取脚本单独使用

无第三方依赖，Python 3.8+ 即可运行：

```bash
python scripts/extract_doc.py <docx路径> <输出目录>
```

输出 `<输出目录>/content.txt`（正文与表格，UTF-8）和 `<输出目录>/media/`（内嵌图片）。

## 自定义

- 团队有固定的设计文档规范时，改 `template.md` 的章节结构即可，`SKILL.md` 不用动。
- 技术栈固定时，在 `checklist.md` 中补充该栈的高频陷阱（如特定框架的事务传播、特定存储的一致性语义）。
- 领域偏移时（如纯数据平台、端侧应用），替换 `template.md` 第 4 章「接口契约」为该领域的契约形态。
