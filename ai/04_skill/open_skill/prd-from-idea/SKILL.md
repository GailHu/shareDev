# 从想法生成 PRD

想法和 PRD 之间的差距不是字数，是信息类别。想法通常只有 How（一个方案），缺 Why（真问题）、缺成功判据、缺边界。直接把想法扩写成文档，产出的是一份看起来完整、但无法用来否决提案、无法验收、无法排期的废页。

PRD 只交付三样东西：**共识、判据、边界**。任何一段文字若既不影响决策、又无法被验证、也不划定边界，就删掉。

## 工作流程

### 第 1 步：把想法还原成问题

用户给的是解决方案，不是需求。先反向还原，否则整份 PRD 会围着一个可能错误的方案打转。

逐层追问并把答案写下来：

| 层级 | 要还原出什么 |
|------|------|
| 表层 | 想法本身（用户说要做什么） |
| 动机 | 他期望消除的具体困扰，以及这困扰发生的频率 |
| 现状 | 在没有这个功能之前，人们怎么凑合着解决（替代方案） |
| 本质 | 这是个体偏好还是群体痛点；有没有更优的解法 |

**伪需求特征**：找不到"现在怎么凑合"的答案（说明痛点不真实或频率极低）；只有一个人提出且无法举出具体发生过的事例；把"想要一匹更快的马"当成需求本身。命中就在 PRD 的「背景」里如实写出质疑，不要静默替用户圆场。

如果还原后发现**更优解法**与原想法不同，在 PRD 第 1 节写明两者，并在「决策记录」里给出选择理由。不要悄悄替换用户的想法。

### 第 2 步：判定规模档位

档位决定写哪些章节，避免小改动配一份 30 页文档。

| 档位 | 判据 | 章节 |
|------|------|------|
| **S** | 单点功能，单人可实现，出错可回滚且无数据残留 | 一页纸：背景与问题、目标与指标、范围、用户故事与验收标准、开放问题 |
| **M** | 涉及多模块或多方并行，或改动用户可见流程 | 全量章节，功能详述只展开关键路径 |
| **L** | 新产品、新系统，或引入不可逆的数据模型与外部依赖 | 全量章节 + 决策记录 + 依赖与风险详表 |

不确定时取高一档。

### 第 3 步：一轮批量澄清，只问一次

把所有缺口一次性列出来问，**每个问题都自带默认假设**，用户可以只回答其中几个，或直接说"按默认"。上限 7 个问题。

优先问这些（按信息价值排序）：

1. 谁的什么痛点？他们现在怎么凑合解决？
2. 上线后用哪个数字判断它成功了？多久之后看？
3. 首版必须覆盖哪一个完整闭环？明确不做什么？
4. 硬约束有哪些：合规、性能上限、必须兼容的系统、必须复用的既有能力？
5. 涉及哪些角色，权限差异在哪？
6. 量级：用户数、数据量、并发峰值？
7. 依赖哪些外部团队或系统？

**禁止多轮追问。** 第一轮没答上来的，全部写进 PRD 的「开放问题」，格式为「问题 + 影响范围 + 本文采用的默认假设 + 需谁在何时确认」，并标注确认后升版。信息缺失不阻塞产出。

### 第 4 步：先定成功判据，再写功能

顺序不能反。先有指标，功能才有取舍依据；先写功能，后补指标，必然堆功能。

- **北极星指标**：单一、面向用户价值、领先于业务结果。
- **输入指标** 3–5 个：团队能直接影响的过程量。
- **护栏指标**：为了主指标不许被牺牲的东西（如转化率提升不得让投诉率上升、不得让首屏变慢）。缺了护栏指标，优化会伤害产品。

每个指标写清**计算口径和数据来源**。口径不写，上线后各方会用不同算法得出相反结论。

指标必须能改变行为：如果这个数字变差你也不会做任何事，它就是废指标，删掉。

### 第 5 步：划边界

三件事都要写，缺一不可：

- **包含范围**：本版要实现的。
- **排除范围**：明确不做的，附一句原因。这是 PRD 最常被漏掉、却价值最高的部分——它是实现期拒绝需求渗入的唯一依据。
- **MVP 分级**：Must（最小闭环，约 60%）/ Should（增强，20%）/ Could（加分，15%）/ Won't（本次不做，5%）。Must 必须自身构成闭环，删掉任何一条都跑不通。

同时建**术语表**。"订单""用户""有效""已完成"这类词是需求歧义的最大单一来源，同一概念在文档里只许有一个名字。

### 第 6 步：展开功能，穷尽异常

每个功能按固定结构写：功能描述一句话、前置条件、主流程（编号步骤）、异常流程、后置状态、权限规则、状态机（若有状态流转）。

写完主流程后，用这张表逐项扫描。**这一步产出的条目通常比主流程更多，也是 PRD 质量的分水岭**：

| 常被漏掉的 | 扫描方法 |
|------|------|
| 逆向操作 | 每个「创建/开启/绑定/提交/授权」是否配了「删除/关闭/解绑/撤回/回收」 |
| 空态与首次使用 | 没有任何数据时界面显示什么，新用户第一次进来看到什么 |
| 并发与幂等 | 两人同时操作同一对象、用户重复点击提交、消息重复投递 |
| 权限越界 | 直接改 URL 或 ID 访问他人数据时的行为；凡「不展示/看不到」的安全要求一律改写为服务端强制 |
| 历史数据 | 功能上线前已存在的数据怎么处理，是否需要迁移或兼容旧格式 |
| 失败可见性 | 异步任务失败时用户怎么知道，能否重试，重试是否安全 |
| 数量上限 | 列表、上传、批量操作的上限是多少，超限提示什么 |
| 时间与时区 | 跨时区、跨天边界、夏令时的口径 |
| 多端一致 | 同一账号在多设备上的状态如何同步，冲突以谁为准 |
| 外部依赖不可用 | 降级放行还是阻断，降级期间的数据如何补偿 |

### 第 7 步：量化非功能需求

不写就等于默认没有要求，而性能与安全事后补极贵——它们牵扯架构。

覆盖：性能（响应时间带分位数）、容量、可用性、安全与合规、兼容性、可运维性（日志、告警、开关）。

写的时候逐句消灭形容词：

| 模糊表述 | 改写为 |
|------|------|
| 加载要快 | 4G 网络下首屏 ≤ 1.5s（P95） |
| 支持大量数据 | 单账号最多 10 万条，列表分页 50 条/页 |
| 及时通知 | 事件发生后 30s 内送达，送达率 ≥ 99% |
| 友好的错误提示 | 列出每个错误码对应的具体文案与触发条件 |
| 尽量兼容主流浏览器 | Chrome / Edge 最近两个大版本，iOS 15+ |
| 高可用 | 月度可用性 ≥ 99.9%，单次故障恢复 ≤ 15min |

**给下游留接口**：硬约束尽量写成带数字、含「必须 / 禁止 / 不得 / 仅」的独立句子，便于后续用 `tech-roadmap-from-prd` 直接提取编号。

### 第 8 步：风险、依赖、决策记录

- **风险表**：风险、概率、影响、缓解措施。区分真问题、被夸大的担忧、以及没人敢说出口的隐忧——第三类最值得深挖。
- **外部依赖**：依赖方、所需交付物、需要的时间点、拿不到时的退路。
- **决策记录**：做过的选择、考虑过的备选、放弃的理由。这条价值最高也最常缺失，它让半年后的人不必重开同一场讨论。

## 边界：什么不写进 PRD

PRD 写 What / Why 加约束，详细设计写 How。混在一起会过早锁定实现，还会让评审失焦——业务方看不懂，技术方只盯技术细节，该对齐的目标和边界反而没人讨论。

| 属于 PRD | 属于详细设计 |
|------|------|
| 数据要素、字段含义、业务规则 | 表结构、索引、缓存策略 |
| 接口要满足的行为与错误语义 | 接口路径、参数名、协议 |
| 性能与一致性要求 | 用什么队列、什么算法达成 |
| 状态机的业务含义 | 状态持久化方式 |

用户如果同时要详细设计，PRD 定稿后另起一份文档，不要合并。

## 输出

按 [template.md](template.md) 的结构撰写，文件名 `<项目名>-PRD-v0.1.md`，默认写入当前工作区根目录。

给用户的回复里点明四件事：还原出的真问题（以及它和原始想法的差异）、成功指标、砍到 MVP 之后剩下什么、哪些开放问题在等确认。不要复述文档目录。

## 交付前自检

七条全过才算完整，任一不过就回去改：

1. **可证伪** — 每条需求都能写出「通过 / 不通过」的检验方法。
2. **无歧义** — 全文搜一遍「大概、可能、尽量、适当、友好、快速、大量、灵活」，逐个替换为数字或具体行为。
3. **闭环** — 每个正向操作都有逆向、异常、超时、越权路径。
4. **边界显式** — 写了排除范围，且每条附原因。
5. **唯一真值** — 同一规则只在一处定义，别处引用，不复制粘贴。
6. **可追溯** — 每条需求能连回某个目标和指标；连不上的，要么删，要么补目标。
7. **有优先级** — 每条需求标了 Must / Should / Could / Won't。

补充检查项：

- [ ] 第 1 步的问题还原写进了文档，不是只在对话里说过
- [ ] 指标有计算口径和数据来源，且每个都能改变行为
- [ ] 异常扫描表十项逐项过了一遍
- [ ] 形容词已清零，非功能需求全部带数字
- [ ] 未知信息进了开放问题，而不是被静默假设
- [ ] 没有表结构、接口路径、缓存策略混进来
- [ ] 档位与篇幅匹配：S 档没有写成长文
