# tech-roadmap-from-prd

一个 Agent Skill：把需求文档（PRD、需求说明、设计草案）转成一份**可否决提案、可应对变化、可事后复盘**的技术路线文档。

## 它解决什么问题

大多数"技术路线"写完就变成归档文档，原因是只写了结论没写依据。这个技能强制产出的每条决策都带六个要素：

| 要素 | 缺失的后果 |
|------|------------|
| 选择 | — |
| 依据 | 无法判断决策是否合理 |
| **排除** | 路线无法否决任何提案，每次都要重开讨论 |
| **前提** | 不知道决策依赖什么事实 |
| **重评触发** | 前提变了没人知道该不该改 |
| **验证节点** | 事后无法判断当初是对是错 |

配套三条交付前自检：能不能用它直接否决一个提案？前提变了改不改？半年后能不能判断当初的决策是对是错？三条都答不上来，产出的就只是说明文档。

## 安装

把 `tech-roadmap-from-prd` 整个目录放到下面任一位置：

| 范围 | 路径 |
|------|------|
| 个人（所有项目可用） | `~/.cursor/skills/tech-roadmap-from-prd/` |
| 项目（随仓库共享） | `<仓库根>/.cursor/skills/tech-roadmap-from-prd/` |

Windows 的个人技能目录为 `C:\Users\<用户名>\.cursor\skills\`。

> 不要放进 `~/.cursor/skills-cursor/`，该目录由 Cursor 内置技能占用。

安装后重启或新开一个对话即可生效。

## 使用

**自动触发**：直接给出需求文档并提出要求即可，例如

```
g:\docs\xxx产品-PRD.docx 根据这个需求文档帮我出一份完整的技术路线
```

**显式调用**：在对话中点名 `tech-roadmap-from-prd`。

若不希望自动触发，在 `SKILL.md` 的 frontmatter 中增加一行：

```yaml
disable-model-invocation: true
```

## 目录结构

```
tech-roadmap-from-prd/
├── SKILL.md                 # 主流程：六步工作法与交付前自检
├── template.md              # 技术路线文档骨架，共 10 章
├── README.md                # 本文件
└── scripts/
    └── extract_doc.py       # .docx 正文、表格与内嵌图片提取
```

## 工作流程概览

1. **读取需求文档** — `.docx` 走提取脚本，并逐张读出内嵌图片（状态机与原型图常含正文没有的细节）
2. **补齐上下文** — 同一需求的旧版本、原型代码、目标项目代码仓库
3. **提取硬约束并编号** — 随后立刻做六类矛盾扫描
4. **识别关键决策** — 只收"回退成本随时间上升"且"影响多方并行"的事项
5. **按依赖排阶段** — 契约冻结 → 垂直切片 → 抽象验证 → 扩量 → 外围收口
6. **写假设、不做清单、待确认前提** — 信息缺失不阻塞产出

## 提取脚本单独使用

无第三方依赖，Python 3.8+ 即可运行：

```bash
python scripts/extract_doc.py <docx路径> <输出目录>
```

输出 `<输出目录>/content.txt`（正文与表格，UTF-8）和 `<输出目录>/media/`（内嵌图片）。

## 自定义

- 团队有固定的技术路线文档规范时，改 `template.md` 的章节结构即可，`SKILL.md` 不用动。
- 领域固定（如只做后端服务、只做数据平台）时，可在 `SKILL.md` 第 4 步的关键决策清单中补充该领域高频的决策维度。
- 需求文档格式固定（如统一用 Confluence 导出）时，可在第 2 步补充该来源的检索约定。
