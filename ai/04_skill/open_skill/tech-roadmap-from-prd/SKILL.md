# 从需求文档生成技术路线

技术路线不是项目排期，不是架构设计文档，也不是技术选型清单。它只回答三件事：哪些关键决策现在必须定下来、依据是什么、什么信号说明这条路走错了。产出必须通过末尾的三问自检，否则只是一份说明文档。

## 工作流程

### 第 1 步：读取需求文档

`.docx` 用脚本提取（Read 工具不支持该格式），脚本位于本技能目录下，调用时拼成绝对路径：

```bash
python scripts/extract_doc.py <文档路径> <输出目录>
```

输出 `content.txt`（正文与表格）和 `media/`（内嵌图片）。用 Read 工具读 content.txt，并**逐张读 media 下的图片**——状态机流程图和界面原型常含正文里没有的交互细节与字段。

`.pdf`、`.md`、`.txt` 直接用 Read 工具。

### 第 2 步：补齐上下文

在需求文档的同级与上级目录检索这三类材料：

- **同一需求的其他版本**（v1.0 / v1.1 / v1.2）。新版本常做减法，**旧版本往往保留着被移出正文的实例清单、非功能需求、埋点方案和风险表，这些恰恰是技术路线最重要的输入**。不要只读最新版。
- **原型代码**。数据模型、字段命名、状态流转的事实来源，比正文描述更准确。
- **目标项目的代码仓库**。决定关键决策是「继承既有技术栈」还是「新增」。

找不到代码仓库不要停下追问，记为待确认前提（第 6 步处理）。

### 第 3 步：提取硬约束并编号

逐条扫描需求文档，抽出**不可协商**的约束，编号 C1、C2……后续每条决策都必须引用约束编号。

识别特征：带数字的指标、含「必须 / 禁止 / 不得 / 仅」的句子、状态机、安全要求、兼容性要求。产品愿望（「体验流畅」「界面统一」）不是硬约束。

**编号完立刻做矛盾扫描。这是挖到关键决策最高效的一步**，需求文档的内部冲突几乎总是指向一个必须现在定的技术决策：

| 常见矛盾 | 扫描方法 |
|------|------|
| 非功能需求的耗时上限与功能描述的「同步返回」冲突 | 把最长耗时与网关、负载均衡、浏览器的默认超时对照 |
| 「不重复开发」目标与实例间的实际差异冲突 | 逐个实例核对输入输出，不要相信分组标题给出的相似性 |
| 「立即生效」与缓存或异步同步机制冲突 | 给每条可见性要求标出允许的延迟上限，区分对称与不对称要求 |
| 访问限制被写成前端行为 | 凡「不渲染 / 不展示 / 看不到」的安全要求，一律搬到服务端强制 |
| 排序或统计要求引入写热点 | 找出高频写、低频读且对实时性无要求的字段 |
| 「已部署」「已上线」类校验依赖人工登记 | 检查该事实能否由自动化流程派生，人工登记必然漂移 |

### 第 4 步：识别关键决策

**判据：只有同时满足「回退成本随时间显著上升」和「影响多方并行工作」的事项才进技术路线。** 其余是实现细节，交给详细设计，写进来只会稀释密度。

按下列清单逐项检查，命中就写成一条决策：

- 数据真值来源与一致性机制（谁是事实，谁是投影，不一致时以谁为准）
- 同步与异步的边界、超时与重试策略
- 抽象层次与复用边界（按哪个维度复用，哪个维度不复用）
- 状态可见性（快照、缓存、失效时机）
- 鉴权与访问限制的强制点（服务端还是客户端）
- 敏感数据的流向与落地范围
- 外部依赖的故障域隔离
- 技术栈继承还是新增（默认继承，新增需举证）

每条决策按六要素写，缺一不可：

```markdown
### D<n> <一句话概括决策>

- **选择**：具体做法，细到能据此写代码
- **依据**：引用约束编号，配量化理由
- **排除**：明确否掉的备选方案及原因（没有这行，路线无法否决提案）
- **前提**：本决策成立所依赖的事实
- **重评触发**：什么条件出现时必须重新评估（没有这行，前提变了无人知道该改）
- **验证节点**：在哪个阶段、用什么方法验证对错（没有这行，事后无法复盘）
```

### 第 5 步：按依赖排阶段，不按人力排

阶段次序由依赖关系决定。通用骨架：

1. **契约冻结** — 多方并行所依赖的接口、数据结构、枚举、错误码。契约不冻结就并行，等于约定返工。
2. **垂直切片** — 挑链路最短的一个场景端到端打通。选型标准是链路完整而业务最简，这样暴露的都是链路级问题，不被业务复杂度干扰。
3. **抽象验证** — 每类各做一个，验证第 4 步的复用决策是否成立。**必须排在扩量之前**，否则抽象一旦失败就是批量返工。
4. **扩量** — 纯增量，可多人并行。设工时熔断线：连续若干个超出预估即停止扩量，退回上一阶段重做抽象。
5. **外围收口** — 反馈、埋点、定时任务、降级演练。

每个阶段写**门禁**：可测量、不通过不得进入下一阶段。

### 第 6 步：假设、不做清单、待确认前提

- **假设与证伪信号**：每条假设配一个可观测的证伪信号，以及触发后的具体动作。
- **明确不做**：让后续提案可以被直接否决，不必每次重开讨论。
- **待确认前提**：信息缺失不阻塞产出。写成「待确认项 + 影响范围 + 默认假设」，标注确认后升版。**不要因为缺信息就反复追问用户，也不要静默假设。**

## 输出

按 [template.md](template.md) 的结构撰写，文件名 `<项目名>-技术路线-v0.1.md`，默认写入当前工作区根目录。

给用户的回复里要点出三样东西：这份路线的核心判断是什么、从需求文档中挖到的矛盾或陷阱是什么、还有哪些前提待确认。

## 交付前自检

三问全过才算技术路线：

1. **能否用它直接否决一个提案？** 检查每条决策是否都有「排除」行和可测量阈值。文中出现「兼顾」「按需」「灵活选择」「适当」即不合格。
2. **前提变了改不改？** 检查每条决策是否都有「前提」与「重评触发」。
3. **半年后能否判断当初是对是错？** 检查成功判据与证伪信号是否可测量，且大部分能在扩量阶段前得出结论。

补充检查项：

- [ ] 每条决策都引用了硬约束编号
- [ ] 矛盾扫描表的每一类都过了一遍
- [ ] 阶段次序由依赖推出，且抽象验证排在扩量之前
- [ ] 每个阶段都有可测量的门禁
- [ ] 未知信息进了待确认前提，而不是被静默假设
- [ ] 决策条目控制在 15 条以内，实现细节没有混进来
