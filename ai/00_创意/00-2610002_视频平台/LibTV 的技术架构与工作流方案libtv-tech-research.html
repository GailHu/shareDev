1. 平台概览与定位

LibTV 是 LiblibAI 推出的专业 AI 视频创作平台，核心理念是"创作，只需要一张画布"。它将传统线性 Prompt 生成模式转变为结构化的影视生产流程，通过无限画布 + 节点式工作流的方式，让创作者像搭积木一样组装视频生产管线。

本次调研目标：分析 LibTV 的技术架构与工作流方案，设计一套面向内部批量生产场景的视频工作流平台技术方案，包含可落地的技术选型、架构设计和实施路线。

2.3 核心设计决策

为什么选 DAG 而非线性管道？

LibTV 的分镜组天然是多分支结构——同一脚本拆出的多个镜头可以并行渲染，合成节点等待全部分镜完成后才执行。DAG（有向无环图）模型能自然表达这种并行依赖关系，而线性管道只能串行。在批量生产场景下，多分支并行渲染可将总耗时缩减 60%。

为什么用异步任务队列而非同步调用？

视频生成是高计算负载的长耗时任务（单次 15 秒视频可能需要 2-5 分钟），同步请求必然超时。采用 Celery + Redis 的生产者-消费者模式：API 网关接收请求后立即返回任务 ID，Worker 进程异步消费任务，前端通过 WebSocket 轮询进度。这是 AI 长时任务的黄金标准架构。

DAG 执行引擎核心设计

# workflow_engine.py — DAG 拓扑排序 + 并行调度

import asyncio
from dataclasses import dataclass, field
from typing import Any

@dataclass
class WorkflowNode:
    id: str
    type: str          # script / image / video / audio / compose
    data: dict[str, Any]  # 节点参数
    dependencies: list[str] = field(default_factory=list)  # 上游节点 ID

@dataclass
class WorkflowContext:
    task_id: str
    results: dict[str, Any] = field(default_factory=dict)  # node_id -> output
    variables: dict[str, Any] = field(default_factory=dict) # 模板变量

class DAGExecutor:
    """DAG 拓扑排序 + 异步并行执行"""

    def __init__(self, nodes: list[WorkflowNode], node_handlers: dict):
        self.nodes = {n.id: n for n in nodes}
        self.handlers = node_handlers  # type -> async callable

    async def execute(self, ctx: WorkflowContext) -> dict:
        # 拓扑排序
        sorted_nodes = self._topological_sort()
        # 按层并行执行
        for layer in sorted_nodes:
            tasks = [self._run_node(nid, ctx) for nid in layer]
            await asyncio.gather(*tasks)
        return ctx.results

    def _topological_sort(self) -> list[list[str]]:
        """Kahn 算法分层拓扑排序，同层可并行"""
        in_degree = {nid: len(n.dependencies) for nid, n in self.nodes.items()}
        layers = []
        while in_degree:
            layer = [nid for nid, d in in_degree.items() if d == 0]
            layers.append(layer)
            for nid in layer:
                del in_degree[nid]
                # 减少下游节点入度
                for other in self.nodes.values():
                    if nid in other.dependencies:
                        in_degree[other.id] -= 1
        return layers

    async def _run_node(self, node_id: str, ctx: WorkflowContext):
        node = self.nodes[node_id]
        # 注入上游结果作为输入
        inputs = {dep: ctx.results.get(dep) for dep in node.dependencies}
        handler = self.handlers[node.type]
        result = await handler(node, inputs, ctx)
        ctx.results[node_id] = result

多级队列设计（关键）

生产实践要点：Celery Worker 预取乘数必须设为 1。默认值会导致一个 Worker 一次抓取多个任务，对于需要数分钟的 AI 视频生成任务，会造成其他 Worker 闲置而队列积压。这是 Celery + AI 场景最常踩的坑。

# celery_config.py — 多级队列 + 关键配置

from celery import Celery

app = Celery('video_workflow', broker='redis://localhost:6379/0')

# === 关键配置 ===
app.conf.update(
    # 预取乘数=1（AI长时任务必须）
    worker_prefetch_multiplier=1,
    # 可见性超时 30 分钟（视频生成可能需要较长时间）
    broker_visibility_timeout=1800,
    # 延迟确认（Worker 崩溃后任务自动回队列）
    task_acks_late=True,
    # 任务级超时
    task_time_limit=600,       # 硬超时 10 分钟
    task_soft_time_limit=480,  # 软超时 8 分钟，触发清理
    # 重试配置
    task_default_retry_delay=15,
    task_max_retries=3,
)

# === 多级队列定义 ===
app.conf.task_routes = {
    # 短任务（图片/音频）→ fast 队列
    'tasks.generate_image': {'queue': 'fast'},
    'tasks.generate_tts': {'queue': 'fast'},
    # 长任务（视频渲染/3D）→ slow 队列
    'tasks.generate_video': {'queue': 'slow'},
    'tasks.render_3d': {'queue': 'slow'},
    # 合成任务 → compose 队列
    'tasks.compose_video': {'queue': 'compose'},
    # 后台清理 → low 队列
    'tasks.cleanup_*': {'queue': 'low'},

模型适配网关设计

# model_gateway.py — 统一模型接口抽象

from abc import ABC, abstractmethod
from dataclasses import dataclass

@dataclass
class GenerationResult:
    success: bool
    media_url: str = None       # 结果文件 URL
    duration: float = 0         # 视频/音频时长
    metadata: dict = None       # 模型返回的元信息
    error: str = None

class ModelAdapter(ABC):
    """所有模型适配器的基类"""

    @abstractmethod
    async def generate(self, prompt: str, **params) -> GenerationResult:
        ...

    @abstractmethod
    async def check_status(self, task_id: str) -> GenerationResult:
        ...

class KlingAdapter(ModelAdapter):
    """Kling 3.0 API 适配器"""

    async def generate(self, prompt: str, image_url: str = None, **params) -> GenerationResult:
        resp = await self._call_api(prompt, image_url, **params)
        # 返回 task_id，需轮询状态
        return GenerationResult(success=True, metadata={"task_id": resp["task_id"]})

    async def check_status(self, task_id: str) -> GenerationResult:
        resp = await self._poll_api(task_id)
        if resp["status"] == "completed":
            return GenerationResult(success=True, media_url=resp["video_url"],
                                    duration=resp["duration"])
        elif resp["status"] == "failed":
            return GenerationResult(success=False, error=resp["error"])
        return GenerationResult(success=True)  # still processing

class LocalSDAdapter(ModelAdapter):
    """本地 Stable Diffusion 适配器"""

    async def generate(self, prompt: str, **params) -> GenerationResult:
        # 直接调用本地 ComfyUI API 或 diffusers
        from src.inference.sd_pipeline import generate_image
        img_path = await generate_image(prompt, **params)
        return GenerationResult(success=True, media_url=img_path)

# 网关注册表
MODEL_REGISTRY = {
    "kling": KlingAdapter,
    "seedance": SeedanceAdapter,
    "sdxl": LocalSDAdapter,
    "flux": FluxAdapter,
    "cosyvoice": CosyVoiceAdapter,
}

async def call_model(model_name: str, prompt: str, **params) -> GenerationResult:
    adapter_cls = MODEL_REGISTRY[model_name]
    adapter = adapter_cls()
    return await adapter.generate(prompt, **params)

4.2 工作流执行引擎

执行引擎负责将用户编排的 DAG 转化为可执行的任务链，核心流程包括：拓扑排序确定执行顺序 → 同层节点并行调度 → 节点间数据传递 → 错误处理与重试。

flowchart LR A[加载工作流 JSON] --> B[拓扑排序分层] B --> C[Layer 1: 脚本节点] C --> D[并行执行] D --> E{成功?} E -->|是| F[Layer 2: 图片节点 x N] E -->|否| G[错误处理/重试] G --> E F --> H[并行渲染关键帧] H --> I{全部成功?} I -->|是| J[Layer 3: 视频节点 x N] I -->|否| G J --> K[并行图生视频] K --> L[Layer 4: 合成节点] L --> M[FFmpeg 拼接输出] M --> N[保存结果 + 通知]

并行优化策略：分镜组拆出的 N 个镜头节点属于同一层，可以全部并行提交渲染。LibTV 的实践证明多分支并行渲染可将总耗时缩减 60%。在 Celery 中，同一层节点通过 asyncio.gather() 或 group() 并行派发任务。

4.4 批量生产模块

批量生产是内部工具场景的核心需求。设计思路：将工作流编排为模板，通过 CSV 导入变量参数，实现一键批量提交数百个视频生产任务。

flowchart TD A[创建工作流模板] --> B[定义模板变量
标题/角色/风格/时长] B --> C[保存为模板] C --> D[上传 CSV 批量数据] D --> E[解析 CSV → N 组变量] E --> F[创建批量任务
1个batch + N个sub_task] F --> G[调度引擎逐个/并行执行] G --> H[进度实时推送] H --> I[批量下载/导出] 
# batch_producer.py — 批量任务生产者

import csv
import io
from src.models import BatchTask, SubTask

async def create_batch_from_csv(
    template_id: str,
    csv_content: str,
    created_by: str,
    max_concurrent: int = 5  # 最大并行子任务数
) -> BatchTask:
    """从 CSV 创建批量任务"""

    # 1. 解析 CSV
    reader = csv.DictReader(io.StringIO(csv_content))
    rows = list(reader)
    if not rows:
        raise ValueError("CSV 为空")

    # 2. 创建批量任务
    batch = await BatchTask.create(
        template_id=template_id,
        name=f"批量任务 {len(rows)} 条",
        total_items=len(rows),
        variables_csv=csv_content,
        created_by=created_by,
    )

    # 3. 创建子任务
    sub_tasks = []
    for i, row in enumerate(rows):
        sub = await SubTask.create(
            batch_id=batch.id,
            sequence=i,
            variables=row,  # CSV 行数据作为变量
            status='pending',
        )
        sub_tasks.append(sub)

    # 4. 派发到 Celery 队列（控制并发数）
    from src.celery_app import app
    from src.tasks import execute_sub_task

    # 使用信号量控制并发
    for chunk in chunks(sub_tasks, max_concurrent):
        group_tasks = [execute_sub_task.s(str(sub.id)) for sub in chunk]
        app.group(group_tasks).apply_async()

    return batch

5.6 节点卡片架构与自定义开发

本节定义画布编辑器的节点卡片架构——一套声明式的节点定义规范，使新增节点类型只需编写一个 CardDefinition 对象并注册，无需修改工具栏、面板、属性编辑器等任何基础设施代码。上面的交互式 Demo 已完全采用此架构。

CardDefinition 规范

属性类型必填说明
typestring是全局唯一类型标识，如 'script'、'imageUpload'
labelstring是节点在面板/画布中的显示名称
categorystring是面板分组类别：'AI生成' | '素材输入' | '后期合成' | '标注'
colorstring是主题色 hex，用于节点边框/面板圆点/连线着色
iconstring否emoji 图标，显示在节点标题和工具栏按钮中
hasInputboolean否是否有输入端口（默认 true）。标注节点设为 false
hasOutputboolean否是否有输出端口（默认 true）
isAnnotationboolean否标注节点不参与工作流执行（默认 false）。备注、批注类节点设为 true
defaultDataobject是节点创建时的初始属性值（深拷贝使用，避免引用污染）
fieldsFieldDef[]是属性面板字段声明数组，见下表
bodyRendererfunction否自定义节点体渲染函数 (node) => htmlString，省略则回退显示 node.data.model

FieldDef 字段定义规范

每个 fields[] 元素声明属性面板中的一个输入控件：

属性类型说明
keystring对应 node.data 中的属性键名
labelstring输入框前显示的中文标签
typeenum控件类型：见下方支持的类型列表
optionsstring[]仅 type='select' 时必填，下拉选项数组
min / maxnumber仅 type='number' 时可选，数值范围约束
stepnumber仅 type='number' 时可选，步进值
placeholderstring仅 type='text' 时可选，占位提示文字

当前支持的字段类型：

select 下拉选择框 · textarea 多行文本框 · number 数字输入（支持 min/max/step） · text 单行文本输入

8. 总结与建议

技术选型一览

前端 React 18 + Vite 画布 React Flow 12 UI Ant Design 5 状态 Zustand 后端 FastAPI 队列 Celery + Redis 数据库 PostgreSQL 16 对象存储 MinIO 视频合成 FFmpeg 监控 Prometheus + Grafana 向量检索 pgvector

关键设计决策回顾

1. DAG 而非线性管道

视频生产天然是多分支结构（一个脚本拆出多个镜头并行渲染）。DAG 拓扑排序能正确表达并行依赖关系，同层节点并行执行可缩减 60% 总耗时。

2. 异步任务队列 + 多级优先级

视频生成是长耗时任务（2-5 分钟/条），必须异步化。Celery 多级队列（fast/slow/compose/low）按任务时长分流，避免短任务被长任务阻塞。预取乘数=1 是 AI 场景下最关键的配置。

3. 模型适配网关

集成 20+ AI 模型不可能硬编码，必须抽象为统一适配器接口。网关负责路由分发、限流控制、冷启动管理、结果验证（防止 200 但输出无效的部分失败）。

4. 模板化批量生产

内部工具的核心价值是"编排一次，批量复用"。工作流保存为模板后，通过 CSV 导入变量参数即可批量提交数百个任务，并发控制 + 进度推送 + 批量下载构成完整交付链路。

5. 分类重试而非盲目重试

每次重试都是财务决定——一次失败的视频生成消耗了真实的 GPU 时间。按错误类型分类处理：429 精确等待、500 指数退避、400 不重试、超时先检查状态。这套策略可减少 40% 的 API 浪费支出。
